# G.E.M.S. Architecture — Genre Controllers & Gameplay Kit

Area reference split out of the always-loaded core ([ARCHITECTURE.md](../ARCHITECTURE.md)). Loaded on demand: **Read this file before designing or modifying anything in this area.** Runtime quirks live in [GMRT.md](../GMRT.md).

## Genre Controllers & Template Gameplay Systems

The Core built-in systems ([ecs.md](ecs.md)) are genre-agnostic. A playable genre scene layers a **player brain** plus **gameplay systems** on top — these live under **Demo** (the `Platformer` minigame in `Demo/Platformer`; the action-RPG across `Demo/Scene`/`Demo/System`/`Demo/Component`) and are orchestrated by the scene's `step()` (directly, or via its `Pipeline`), not auto-run by `World`.

**The RPG player brain is an ECS system** — **`PlayerSystem`** (Demo/System; the input counterpart of `CombatAI`) driving the **`Playable`** component (Demo/Component). `Playable`'s presence marks THE input-driven entity — every consumer finds the player **live by query** (`PlayerSystem.id(world)`; `sceneRpg.step` re-latches it each frame as `scene.playerId`, also set on boot spawn + portal arrival, so there is no stored player handle to dangle) — and its flat data (`{ fireCd, attackCd, cursorX, cursorY }`) is the brain's per-tick state, riding `EntitySnapshot`/map transfer with the rest of the player sheet. `PlayerSystem.update(world)` runs at the **head of the RPG physics `Pipeline`** (before `SolidSystem` integrates the `Velocity` it writes): movement + sprint (`StaminaSystem`), twin-stick or cursor aim, and the **item-driven attack** — it reads the equipped weapon's composed profile (or, unarmed, the shared fist fallback `PLAYER_FIST`, so unarmed never fires a free bullet) and runs whatever it describes; a gun fires via `RpgPlayer.fireBullet(world, shooterId, opts)` — an instant hitscan shot (`Combat.hitscan`, no projectile entity) returning the normalized aim. Input **lifecycle** stays scene-driven, not simulation: `PlayerSystem.bindKeys()` registers the keymap + `InputContext` tags (boot via `RpgMap._buildWorld`, re-applied on host `resume()`), `PlayerSystem.unbind()` drops it (scene `destroy`), and `PlayerSystem.spawn(world, spawn)` builds the player at this genre's tuning via **`RpgPlayer.spawn`** (Demo — assembles the full sheet, including `Playable` + `Animator`).

**The platformer keeps a genre controller** (`PlatformerController`) — player input + entity setup as a three-phase lifecycle over a plain `ctrl` state bag, not an `update(world)`. It is a movement showcase: it builds a plain player itself (transform + `Collision` + `Direction`/`Grounded`/`Visual`, **no** RPG components) and has no firing.

- `create(world, spawn)` — registers the keymap (`Input.bindAll`), spawns the player, returns the `ctrl` state bag.
- `pollInput(ctrl)` — call **once per frame, before `world.update()`**, outside the tick loop. Samples _edge-triggered_ input (jump `pressed()`/`released()`) into buffers so presses aren't lost on 0-tick frames or double-counted on multi-tick frames. (The RPG brain reads no buffered edges, so `PlayerSystem` has no poll step.)
- `update(world, ctrl)` — call **once per physics tick**. Reads _continuous_ input (movement) and applies acceleration/jump to `Velocity` (before `SolidSystem` integrates it).
- `destroy()` — unregisters input. Plus genre verbs like `respawn`.

Read flags like `Grounded.isGrounded` live off the component each use (the `&&`-clobber quirk, GMRT.md §1).

**Template gameplay systems** are stateless `globalThis` objects like Core systems but expose _named query/resolve methods_ (not `update(world)`), called from `step()` after physics resolves: `EnemySystem` (patrol + stomp/touch resolution) and `CollectibleSystem` (`hitSpike`). They read `col.hits` (filled by `TriggerSystem`) or do their own overlap test, and return values the scene applies to player state. (Platformer-only; the RPG combat/loot systems live in the RPG layer.) `scenePlatformer` is the compact reference orchestration: per tick → `snapshot` → `controller.update` → `physics` Pipeline (`Gravity → clampFall → SolidSystem → TriggerSystem`) → enemy/spike resolution → respawns → `flush`.

**Lobby categories** are `SCENE_CAT_*` i18n keys; `SceneRegistry.add(factory, { label, category })` slots a scene under one.

## Gameplay Kit

The **`Gameplay`** pillar is the reusable, genre-agnostic gameplay kit between `Core` and `Demo` — the systems a second genre reuses unchanged (placement rule: ARCHITECTURE.md → Layers & Placement). Every kit module depends only on `Core` + sibling kit modules — **never on `Demo`** (the demo could be deleted and the kit still builds; this is exactly why `Downed` is in `Combat`, since `FollowerSystem` reads it, while `Portal` stays in `Demo`, since only `RpgMap`/`RpgSpawn` do).

Grouped by **feature module** (component + system colocated, unlike Core's type-split):

- **`Combat`** — the shared damage applier `Combat.applyDamage` (over an injectable `Combat.mitigate` hook), plus `Health`, `Stamina`(+`StaminaSystem`), `Faction`(+`FactionSystem`), `Mortal` + `Downed`, `Projectile`(+`ProjectileSystem`), `MeleeSystem`. Every path lands hp through `Combat.applyDamage`, which subtracts after `mitigate` (default identity — the kit stays stat-agnostic; a game injects its formula). The attack side is composed by the consumer. All paths only SUBTRACT hp; the reaction at ≤0 hp is the `Mortal` death pass (rpg.md → _Death_).
- **`Items`** — the `Item` + `Rarity` + `Manufacturer` registries and the per-item capability components (`Weapon`, `Consumable`(+`ConsumableSystem`), `Container`). "Kinds of item" are a flat `Item` carrying a `components: []` queried by `instanceof`.
- **`Inventory`** — `Inventory`(+`InventorySystem`), `ItemDrop`, `Encumbrance`(+`EncumbranceSystem`).
- **`Equipment`** — `Equipment`(+`EquipmentSystem`), `Equippable`, `AppearanceSystem` (rebuilds the Core `Appearance` paper-doll layer stack from worn gear — rpg.md → _Paper-doll appearance_).
- **`Animation`** — `Animator`, `AnimationSystem` (a data-driven sprite state machine).
- **`Lighting`** — `Light` + `RenderLighting`. The day/night ambient is **injected**: `RenderLighting` takes `opt.ambient: () => { color, alpha }` (default full daylight = inert, early-outs), so the pass carries no day/night opinion; the demo wires `WorldClock.tint` in `RpgMap.build`.
- **`Quest`** — `QuestLog` (quest defs + progress; the Core `UIQuestTracker` widget binds to it via an injected source, so Core never references the kit).
- **`Crafting`** — `CraftSystem` + `Recipe`.
- **`Squad`** — `Squad` (membership: entities sharing a squad id travel together) + `Follower`(+`FollowerSystem`) (companion follow/wait behavior, hire/kick membership transitions, carry bonus).
- **`NPC`** — the `NPC` dialogue-character component (pairs with Core's `Dialogue` singleton).
- **`Status`** — the buff/debuff layer: `Status` (def registry) + `StatusEffects` (component) + `StatusSystem`. Stat-model-agnostic: a `mods`-bearing status folds into the derived sheet via an **injected** `StatusSystem.onStatsChanged` hook, mirroring `Combat.mitigate`. See rpg.md → _Buffs & statuses_.
- **`Survival`** — the needs layer: `Thirst`/`Hunger`/`Drowsiness` components + per-need systems over a shared `Survival` core. A need is a rising meter that, at its `critical` threshold, applies a debuff **`Status`** (depends on the `Status` sibling); restored by drinking/eating/sleeping. See rpg.md → _Survival needs_.
- **`Interaction`** — the "walk near + press E" layer: the `Interaction` component (`{ kind, ...params }`) + the **`InteractAction`** registry (`register([{ id, prompt, run(ctx) }])`). The `kind` names a registered action; `run(ctx)` does anything, so the mechanism is data, not a hardcoded switch. The registry holds no concrete actions (the RPG registers `RpgInteractions`), and the generic pick/prompt/dispatch **engine** is Demo/UI `Interactable` (it reads Demo windows, so it stays in Demo). See rpg.md → _Interactions_.
- **`Trade`** — the merchant layer: `Merchant` (a trade-config component pairing with the entity's own `Inventory` = its stock) + `TradeSystem` (price/buy/sell/restock). Currency-agnostic: the money is the `Merchant.currencyId` item, so the kit names no specific currency. Two modes by `Merchant.infinite` — infinite (bottomless stock + wallet) or finite (real stock + a wallet that gates buying, `TradeSystem.update` restocking toward a `template` every `restockSecs`). Prices: `marketValue = round(Rarity.modify(rarity, value))`, buy `= ceil(market·buyMargin)`, sell `= floor(market·sellMargin)`. The kit↔Demo split mirrors `Crafting`/`CraftingUI` (the demo window is `TradeUI`).
- **`Settlement`** — the territory layer: a settlement **is a `Zone`** in the `"settlement"` `ZoneMap` channel (its painted cells = its lands) carrying flat `data` `{ sid, factionId, color, comp }` + a `name`. A stateless namespace (`found`/`at`/`atWorld`/`ownerAt`/`all`/`byId`/`expand`/`centroidWorld` + capability helpers) with **Core-only deps**, holding **no policy** on which faction is "the player" (the consumer decides — `BuildMode.OWNER`). Every settlement has a stable **`sid`** — minted `uuid()` for player-founded, authored id (`meta.settlements[].id`) for level-file ones — the key everything else references; multiple settlements per map coexist. Collaborators: **`SettlementComponent`** (the capability-def registry; a settlement's capabilities are a flat comma-joined id list in `zone.data.comp` — JSON-safe), **`Resident`** (a `{ settlementId }` membership component exactly like `Squad`, attached **explicitly** by a spawn descriptor's `settlement: <sid>` field — no auto-by-location), and **`SettlementSystem`** (stateless glue: `residents` is a live query, never a stored roster; `storageOf` = the resident with a `"storage"` `Interaction`). Build gating: rpg.md → _Genre UI managers → BuildMode_.

The per-module **behavior** is documented in detail in _Gameplay / RPG Layer_ ([rpg.md](rpg.md) — the RPG scene is the reference consumer); this section is the membership + the kit→Core dependency contract.
