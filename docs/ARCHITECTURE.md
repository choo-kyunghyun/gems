# G.E.M.S. Architecture

## Overview

This file carries the layer map, the cross-cutting invariants, and the area index — and nothing per-module: a module's contracts live in JSDoc at its owning declaration (CLAUDE.md → Comments law 2).

Routing rule: the code is the primary reference. Before designing or modifying an area, read its owning files' JSDoc contracts, the invariants here, and the quirks in GMRT.md. The per-area ledgers that used to sit under `docs/architecture/` are gone — their contracts now live at the owning declarations (CLAUDE.md → Comments law 2). The index below exists only to locate an area's owning files; a new contract goes to its owner, never here.

Doc laws — what this file may contain:

1. Only cross-cutting facts: the layer map, invariants binding every area, and the area index. A single-module contract lives in that module's JSDoc, never here.
2. No history. What a design replaced, when, and why lives in git — never in docs.
3. One owner per fact: GMRT quirks in GMRT.md, cross-cutting invariants here, a module contract at its owning declaration. Everyone else cites.
4. No API inventories, content catalogs, or tutorials — signatures and contracts live in JSDoc, content in its registry, GameMaker in the manual.
5. Dead or unwired code gets a clause, not a paragraph.

## Layers & Placement

The project's largest systems are the ECS system and the Flexpanel-based UI system.

Four top-level pillars (project folders), each reusable without the ones after it:

- `Core` — the pure engine: ECS (the `Entity` store + the `World` manager singleton), levels/zones, renderer passes, the UI system, input, utilities. References only engine concepts.
- `Gameplay` — the genre-agnostic gameplay kit (`Combat`/`Items`/`Inventory`/`Equipment`/`Animation`/`Lighting`/`Quest`/`Crafting`/`Squad`/`NPC`/`Status`/`Survival`/`Trade`/`Interaction`/`Settlement`/`Environment` — the last being the world-sim: `WorldClock`/`Weather`/`Temperature`). Imposes a gameplay model but names no specific content, and each module colocates its component + system (unlike Core's type-split). Every kit module depends only on Core + sibling kit modules, NEVER on Demo (the demo could be deleted and the kit still builds).
- `GemsUI` — the themed UI factory kit (`GemsTheme`/`GemsContainers`/`GemsWidgets`/`GemsControls`) over the Core UI system.
- `Demo` — the integrated showcase consuming the other three: the app shell, the scenes (RPG / platformer / editor / lobby), and all content- or model-specific glue (`Rpg*`, `Stats`, `CombatAI`, the world-sim).

**Placement rule** for new code: references only engine concepts → Core; imposes a gameplay model but names no specific content → Gameplay; names specific content/scenes/`Rpg*` → Demo. Read it through the consumers, which is what settles the near calls: `Downed` sits in `Combat` because kit code (`FollowerSystem`) reads it, while `Portal` stays in Demo because only `RpgMap`/`RpgSpawn` do.

## Cross-Cutting Invariants

Rules that apply in every area (the GMRT quirks in [GMRT.md](GMRT.md) additionally always apply):

- **ECS shape**: components are string tokens (`globalThis.Position = "Position"`), each script carrying the `@typedef` that is the only definition of its data shape (they ARE the type system — the checker consumes them); systems are plain objects `{ update(entities) }`, or, for on-demand utility systems (`PathfindingSystem`), stateless objects with named query/resolve methods instead of an `update`; each level owns its `Entity` store, and `World` is the world-manager singleton over it (`World.sim` fixed-step clock, `World.levels` level registry) — it holds no entity data and never auto-runs systems; the level's `step()` dispatches them explicitly. (Store handles are canonically `entities`; the ubiquitous legacy `world` name is grandfathered — rename plan: ROADMAP.md → Code Review.)
- **Composition over inheritance** — GMRT breaks subclassing (`super` faults, base-class field initializers don't run — see GMRT.md): "kinds of X" are a flat class plus a `components: []` queried by `instanceof` (`Item`, `UIElement`); scene screens are standalone classes satisfying the duck-typed `Level` contract, never `extends Level`.
- **Singleton shape**: a global with one live instance is a plain object (`globalThis.World = { … }`), state held as ordinary properties — the form the systems and namespaces already use (`World`, `Log`, `Combat`, every `*System`). A static-only class buys nothing here (no instances, no `instanceof`, inheritance broken regardless) and takes on two class-only GMRT defects, the ~50-method cliff (#15065) and the static-initializer trap (GMRT.md): write no new ones. A class with one live instance that owns a lifecycle is NOT a singleton — `LevelManager`/`ChunkManager` are instance classes, shaped and named as such.
- **The clock split (pause/dilation rule)**: `Time.delta` is scaled by `Time.scale`, so anything on it freezes/slows with the sim — gameplay motion wants exactly that, but UI timers/easing must use `Time.raw` (hover/press fades, caret blink, key-repeat, toggle easing — `UIButton`/`UIInput`/`UICheckbox`; likewise the GUI singletons `Toast`/`SceneTransition`/`Dialogue`), else menus freeze while the game is paused. World-space effects deliberately stay on `Time.delta` so slow-mo slows them too (`FloatingText`, `Weather`).
- **Live queries over stored handles**: entity ids are never held across frames/maps — consumers re-derive them by component-presence query each use (`scene.playerId` from `Playable`, the camera target from `CameraFocus`, NPCs/portals/enemies by `world.query`/`Query`). Markers are components, not tag strings.
- **AABB convention**: every collision/geometry consumer derives world-space edges through `AABB.edges(pos, box)` / `AABB.of(entities, id)` — never inline `pos.x + box.x` (the non-uniform BBox anchor lives in one place).
- **Injection idiom**: a Core/kit module stays model-agnostic by exposing a hook the Demo wires at scene setup (`Combat.mitigate`, `StatusSystem.onStatsChanged`, `ConsumableSystem.grantAttr`, `RenderLighting`'s `ambient`, `UIQuestTracker`'s `source`). Extend through the seam; never make the kit reach down into Demo.
- **Registry pattern**: content is data registered into flat registries keyed by string id (`Item`/`Rarity`/`Manufacturer`/`Status`/`Recipe`/`Prefab`/`InteractAction`/`EntityPreset`/`StateSystem`) — adding content is a data entry, not an engine edit. Registration runs from `create()`-time calls (`RpgContent.register()`), never at script top level (load order).
- **Serialization-safe data**: persisted blobs (SaveData/Settings, zone `data`, `world.export`/`EntitySnapshot`) may nest — serialize them with GML `json_stringify` (the interop workaround), or, when the data carries sprite refs or can cycle, the `Json` codec; both are nesting-safe where JS `JSON.stringify` faults (see GMRT.md). The hard rule that remains: no `Set` in serialized fields (GMRT Set iteration crashes). Dense/large arrays still go to binary blobs, not JSON (see `File` / the Snapshot hybrid).

## Area Index (owning files)

Each entry names an area's owning files, so you can find where a contract lives. The contract itself is in the code — read the file, not a summary of it.

- **Demo shell & GemsUI** — `objects/obj_game/` (the per-event wiring; each event's order is a contract), `Level` (the duck-typed screen contract), `LevelManager` (`World.levels` — flat level collection, keep-switch guest minigames, the resident-map registry), `sceneLobby` (boot scene + dev launcher) and `demo` (`SceneRegistry`, `teardownScene`), plus the GemsUI factory kit: `GemsTheme` (palettes + the kit-wide contracts) with the `GemsContainers`/`GemsWidgets`/`GemsControls` factory buckets.
- **ECS core & simulation** — `Entity` (the per-level store) over `EntityData` (SoA) + `EntityID` (generational ids), `EntitySnapshot` (single-entity capture/migrate); fixed-rate simulation in `SimClock` (`World.sim` — ticks + `alpha`, and the tick-loop ordering contract), `Pipeline`, `Time`; the built-in systems, each owning its own contract (`Gravity`/`Movement`/`Solid`/`Separation`/`Trigger`/`State`/`Lifetime`/`Interpolation`/`Pathfinding`); pathfinding via `PathfindingSystem` → `PathFollow` (the consumer-side walker + terrain cost) over `MotionPlanner`/`NavGrid`.
- **Genre controllers** — a genre layers a player brain over the Core systems: the RPG's is an ECS system (`PlayerSystem` driving the `Playable` component, at the head of the scene's physics `Pipeline`), the platformer's a lifecycle controller over a plain `ctrl` bag (`PlatformerController` — `create`/`pollInput`/`update`/`destroy`), plus the template resolve-after-physics systems (`EnemySystem`/`CollectibleSystem`) that `scenePlatformer` orchestrates. The Gameplay kit membership is the layer map above; each module owns its contract in its own JSDoc.
- **The action-RPG** — the reference consumer, and the largest area. `sceneRpg.step` is the reference orchestration; `RpgScene` holds the combat/loot plumbing and the `Mortal` death pair. Content is `Item`/`Rarity`/`Manufacturer` + the capability components (`Weapon`/`Gun`/`Ammo`/`WeaponMod`/…), with `Attributes`→`StatModel` deriving `Stats`, `Combat` applying all damage, and `CombatAI` driving every non-player combatant. Paper-doll art is `Appearance`+`AppearanceSystem` over the `spr_human` strip (template contract in `tools/pixel-art-kit`). Genre UI: `SystemMenu`/`StorageUI`/`TradeUI`/`CraftingUI`/`WeaponModUI`/`BuildMode`/`RpgInventoryUI`/`RpgWorldOverlay`, refresh-driven by `Interactable`. The world-sim is `WorldClock`/`Weather`/`Temperature` (Gameplay/Environment). Persistence: `RpgMap` (the map pool) → `SaveGame` over `Snapshot`+`Json`, with `Blueprint` replaying builds. Streaming/worldgen: `ChunkManager` over a composed `ChunkGenerator` (`AuthoredStamp`/`PrefabStamp`/`OverworldGen`/`TerrainField`/`Prefab`).
- **Level & map layers** — `LevelGrid` (the level's grid data: tile layers + zone channels + world↔grid conversion, held as the legacy `.level`) over the `LevelLayer` interface, whose one implementation is `TileLayer` (a `Grid` of `TileType`); `TileEdit` (the collider-sync service owning the "edit a solid tile → remesh colliders" invariant, greedy-meshed); zones as `Zone`/`ZoneMap` (one channel, one zone per cell) driven by `ZoneSystem` (enter/exit edges).
- **Renderer** — `Renderer` (the ordered `RenderPass` list a scene owns) over the passes, each carrying its own contract: the art projection contract is owned by `RenderBillboard` (STANDING) with `RenderMesh` (VOLUME) and `RenderWalls` (WALLS); ground/tiles are `RenderTileMap` (its `@typedef` documents every autotile mode) and `RenderChunks` over `VertexBuffer`; atmosphere is `RenderCloudShadow`/`RenderWeather`/`RenderLighting` (which owns the screen-space overlay orientation contract); plus `RenderZone`/`RenderGrid`/`RenderDebug*`. `sh_meshlit` is the one world shader and owns the shader-authoring rules.
- **UI & input** — `UIElement` (flexpanel tree + the `UIState` blackboard) under `UI`, which owns the fixed 1920×1080 design resolution, `applyScale`, and the layout guarantee (why no widget carries a NaN guard); the `UIComponent` widgets each document their own contract, with `UITrigger` the canonical pointer FSM and `UIDraw` the shared-primitive bucket (it owns the resolve-fonts-at-draw-time rule); the standalone singletons `Tooltip`/`Toast`/`UIPointer` (owner of the poll-once rule)/`SlotDrag`/`VirtualKeyboard`/`UINav`/`SceneTransition`/`Dialogue`/`FloatingText`; input is `Input`/`InputAction`/`InputContext`, with `Camera.cursorWorld` owning the pitched-camera world-cursor rule.
- **Presets, query & utilities** — `EntityPreset` (declarative spawning, variant inheritance, the `scale`×`size`/density bake) and `Query` (spatial lookup by component presence), over the Core/Util modules, each owning its contract: `Settings`/`Color`/`SpriteMeta` (the declared per-sprite metadata)/`I18n`/`Camera`/`Audio`/`Tween`/`MotionPlanner`/`AABB`/`Broadphase`/`Raycast`/`File` (sync text + binary, async caveats)/`Json` (the ref/cycle-safe codec)/`Snapshot` (the save frame)/`Log`/`Screenshot`/`Debug`/`DebugInspector`/`Utils`.
