# G.E.M.S. Architecture

## Overview

This file carries the layer map, the cross-cutting invariants, and the area index — and nothing per-module: a module's contracts live in JSDoc at its owning declaration.

Routing rule: the code is the primary reference. Before designing or modifying an area, read its owning files' JSDoc contracts, the invariants here, the quirks in GMRT.md, and — for anything on a per-tick or per-entity path — the costs in PERF.md. The per-area ledgers that used to sit under `docs/architecture/` are gone — their contracts now live at the owning declarations. The index below exists only to locate an area's owning files; a new contract goes to its owner, never here.

Doc laws — what this file may contain:

1. Only cross-cutting facts: the layer map, invariants binding every area, and the area index. A single-module contract lives in that module's JSDoc, never here.
2. No history. What a design replaced, when, and why lives in git — never in docs.
3. One owner per fact: GMRT quirks in GMRT.md, cross-cutting invariants here, a module contract at its owning declaration. Everyone else cites.
4. No API inventories, content catalogs, or tutorials — signatures and contracts live in JSDoc, content in its registry, GameMaker in the manual.
5. Dead or unwired code gets a clause, not a paragraph.

## Layers & Placement

The project's largest systems are the ECS system and the Flexpanel-based UI system.

Two top-level pillars (project folders), Core reusable without Game:

- `Core` — the engine, and only the engine: ECS (the `EntityStore`), the `Level`/`Scene`/`World` triad (with `WorldClock`, the in-game calendar `World` advances), the level-generation frame (`LevelGen`, the pass runner — it ships no stage), renderer passes (`RenderLighting` among them, over the `Light` component), sprite playback (`AnimationSystem` for strip sheets, `SkeletonSystem` for Spine rigs), the UI system, input, utilities. Every area references only engine concepts — space, time, presentation, entity lifecycle — and never a gameplay rule. Core never references Game (Game could be deleted and Core still builds).
- `Game` — the integrated showcase consuming Core: the app shell, the scenes (colony / lobby), the whole gameplay model flattened into `Game/Component` (data: `Health`/`Stats`/`Inventory`/`Equipment`/`Faction`/the survival needs/…) and `Game/System` (behaviour + content registries: `Combat`/`InventorySystem`/`StatusSystem`/`Weather`/`Tracker`/`QuestLog`/…), the item vocabulary in `Game/Item` (the `Item`/`Rarity`/`Manufacturer` registries, over the capability classes `Weapon`/`Gun`/`Ammo`/`Equippable`/… they compose, in `Game/Item/Component`), all content- or model-specific glue (`Colony*`, `content*`, `CombatAI`), the worldgen stages and their composition in `Game/Level` (`OverworldGen` over `Gen*`/`PrefabStamp`), the Gems UI kit (`Game/UI/Kit`: the themed factory buckets `GemsTheme`/`GemsContainers`/`GemsWidgets`/`GemsControls` over the Core UI system), and the media assets (`Game/Media`).

Placement rule for new code: references only engine concepts (space/time/presentation/entity lifecycle) → Core; states a gameplay rule — damage, needs, economy, progression — or names specific content/scenes/`Colony*` → Game, data to `Game/Component`, behaviour and registries to `Game/System`, item definitions to `Game/Item`, an item capability class to `Game/Item/Component`, a content data table to `Game/Content` (`content*`, authored as JS — content is code, never a shipped JSON datafile), a level-generation stage to `Game/Level` (the runner is Core; what it runs is content policy). Read it through the consumers, which is what settles the near calls: `AnimationSystem` is Core because Core draw passes (`RenderBillboard`/`RenderEntity`) call it and `WorldClock` because `World` drives it, while `Combat`/`Faction`/`Interaction` are Game because every consumer is.

## Cross-Cutting Invariants

Rules that apply in every area (the GMRT quirks in [GMRT.md](GMRT.md) additionally always apply):

- ECS shape: components are string tokens (`globalThis.Position = "Position"`), each script carrying the `@typedef` that is the only definition of its data shape (they ARE the type system — the checker consumes them); systems are plain objects `{ update(entities) }`, or, for on-demand utility systems (`PathfindingSystem`), stateless objects with named query/resolve methods instead of an `update`; each `Level` owns its `EntityStore`. Nothing auto-runs systems — the active scene's `update()` dispatches them explicitly. (Store handles are canonically `entities`.)
- Level / Scene / World: a `Level` is one map's DATA — its grid and its entity store — and nothing else (it never updates or draws). A `Scene` is the behaviour: it composes a level, systems, renderer, camera and UI, and owns `update()`/`draw()`. `World` pools Levels by map id and carries the cross-map timeline. There is no scene manager: the `Game` object holds the one active scene pointer and drives it from its own events (its Create_0 owns the switch/pause contract). Exactly one scene is live and a switch destroys it — a scene is never frozen, so it carries no state across a swap.
- Composition over inheritance — GMRT breaks subclassing (`super` faults, base-class field initializers don't run — see GMRT.md): "kinds of X" are a flat class plus a `components: []` queried by `instanceof` (`Item`, `UIElement`); scene screens are standalone classes satisfying the duck-typed `Scene` contract, never `extends Scene`.
- Singleton shape: a global with one live instance is a plain object (`globalThis.World = { … }`), state held as ordinary properties — the form the systems and namespaces already use (`World`, `Log`, `Combat`, every `*System`). A static-only class buys nothing here (no instances, no `instanceof`, inheritance broken regardless) and takes on two class-only GMRT defects, the ~50-method cliff (#15065) and the static-initializer trap (GMRT.md): write no new ones. A class with one live instance that owns a lifecycle is NOT a singleton — `LevelGen` is an instance class, shaped and named as such. A family of singletons stays FLAT, grouped by a name prefix and composed by its head at boot/reset (`Audio`/`AudioListener`/`Music`, `World`/`SimClock`/`WorldClock`/`WorldEvents`, `Render*`), and callers reach the leaf directly; a member mirroring a singleton (`X.sub = Sub`) is a second name for one object plus a boot-wiring dependency, so a member only ever holds data (`World.levels`, the level pool).
- The clock split (pause/dilation rule): `Time.delta` is scaled by `Time.scale`, so anything on it freezes/slows with the sim — gameplay motion wants exactly that, but UI timers/easing must use `Time.raw` (hover/press fades, caret blink, key-repeat, toggle easing — `UIButton`/`UIInput`/`UICheckbox`; likewise the GUI singletons `Toast`/`SceneTransition`/`Dialogue`), else menus freeze while the game is paused. World-space effects deliberately stay on `Time.delta` so slow-mo slows them too (`FloatingText`, `Weather`).
- Hot-path idioms: the runtime is a VM, so per-element constants decide the frame, not complexity class ([PERF.md](PERF.md) owns the costs and the full list). The two that bind every area: a per-tick system iterates with `entities.forEach(tokens, fn)` and reads its components off the callback, never `query` + a `get` per entity (`query` stays for a materialised id list that outlives the scan); and geometry in a pair sweep writes into a caller-owned `AABB.rect()` scratch through `edgesInto`/`ofInto` rather than allocating per test.
- Live queries over stored handles: entity ids are never held across frames/maps — consumers re-derive them by component-presence query each use (`scene.playerId` from `Playable`, the camera target and the audio listener's body from `CameraFocus`, NPCs/beacons/enemies by `entities.query`/`Query`). Markers are components, not tag strings.
- AABB convention: every collision/geometry consumer derives world-space edges through `AABB.edges(pos, box)` / `AABB.of(entities, id)` — never inline `pos.x + box.x` (the non-uniform BBox anchor lives in one place).
- Injection idiom: a module stays model-agnostic by exposing a hook its consumer wires at scene setup — Core to Game (`RenderLighting`'s `ambient`, `UIQuestTracker`'s `source`) and, inside Game, a system to the scene that owns the stat model (`Combat.mitigate`, `StatusSystem.onStatsChanged`, `ConsumableSystem.grantAttr`, all wired in `sceneColony.create`). Extend through the seam; never make Core reach down into Game.
- Registry pattern: content is data registered into flat registries keyed by string id (`Item`/`Rarity`/`Manufacturer`/`Status`/`Recipe`/`Prefab`/`InteractAction`/`EntityPreset`/`StateSystem`) — adding content is a data entry, not an engine edit. Registration runs from `create()`-time calls (`content.register()`), never at script top level (load order). The id-keyed, insertion-ordered ones are thin facades over the shared `Registry` ops, which own that store's contract.
- Serialization-safe data: persisted blobs (Settings/InputPreset, `entities.export`/`EntitySnapshot`) may nest — serialize them with GML `json_stringify` (the interop workaround), or, when the data carries sprite refs or can cycle, the `Json` codec; both are nesting-safe where JS `JSON.stringify` faults (see GMRT.md). The hard rule that remains: no `Set` in serialized fields (GMRT Set iteration crashes). Dense/large arrays still go to binary blobs, not JSON (see `File` / the Snapshot hybrid).

## Area Index (owning files)

Each entry names an area's owning files, so you can find where a contract lives. The contract itself is in the code — read the file, not a summary of it.

- Game shell & UI kit — `objects/Game/` (the per-event wiring; each event's order is a contract, and Create_0 owns the scene pointer + its switch/pause lifecycle), `Scene` (the duck-typed screen contract) with `SceneTransition` (the swap fade), `sceneLobby` (boot scene + dev launcher) and `demo` (`SceneRegistry`, `teardownScene`), plus the Gems UI kit: `GemsTheme` (palettes + the kit-wide contracts) with the `GemsContainers`/`GemsWidgets`/`GemsControls` factory buckets and the gems-composed overlay singletons `GameOverlay` (the app's pause overlay, a side sheet over the right half of the screen — the Game object hands itself to its update(), and its quit target is boot-wired) and `VirtualKeyboard`.
- ECS core & simulation — `EntityStore` (the per-level store) over `ComponentStore` (SoA columns) + `EntityID` (generational ids), `EntitySnapshot` (single-entity capture/migrate), and `World` (the map-id → `Level` pool, whole-entity take/put/transfer between them, and the world timeline it delegates to `WorldClock`/`WorldEvents`); fixed-rate simulation in `SimClock` (ticks + `alpha`, and the tick-loop ordering contract) and `Time`; the built-in systems, each owning its own contract (`Movement`/`Solid`/`Separation`/`State`/`Lifetime`/`Interpolation`/`Pathfinding`/`Animation`/`Instance`/`Skeleton`); pathfinding via `PathfindingSystem` → `PathFollow` (the consumer-side walker + terrain cost) over `MotionPlanner`/`NavGrid` (the level-sized cost grid every agent shares — tile costs mirrored on the layers' edit count, colliders stamped from `SolidSystem`'s static snapshot through its `onStatics` hook; no polling, no per-agent window).
- Genre controllers — a genre layers a player brain over the Core systems: the colony's is an ECS system (`PlayerSystem` driving the `Playable` component, at the head of the scene's physics sequence). A genre picks the `Game/System` modules it wants, and each module owns its contract in its own JSDoc.
- The colony sim — the reference consumer, and the largest area. `sceneColony.update` is the reference orchestration; `ColonyCombat` holds the combat/loot plumbing and the `Mortal` death pair. Content is `Item`/`Rarity`/`Manufacturer` + the capability components (`Weapon`/`Gun`/`Ammo`/`WeaponMod`/…), with `Attributes`→`StatModel` deriving `Stats`, `Combat` applying all damage, and `CombatAI` driving every non-player combatant. Doll art is `Appearance`+`AppearanceSystem` dressing the `spineHuman` rig by slot, over the puppet `SkeletonSystem` poses; the rat is the undressed second rig (`spineRat`), and `ColonyPlayer.RIGS` maps actor state to each rig's animation set. Genre UI: `StorageUI`/`TradeUI`/`CraftingUI`/`WeaponModUI`/`WorldMapUI`/`BuildMode`/`InventoryUI`/`WorldOverlay`, refresh-driven by `Interactable`. The world-sim is `Weather`/`Temperature` over the Core `WorldClock`, with `RenderWeather`/`RenderCloudShadow` reading them; a level's `meta.climate` (a forced condition + temperature offset) pins the sky over the whole map while it is the active one — `ColonyMap` applies it on every arrival, and nothing tracks position within a map. A settlement is likewise a whole level (`Settlement`): its record — owner faction, name, capability ids — is per-map scene state authored by `meta.settlement` or founded at a Survey Post, its identity the map id its `Resident` members carry, and `BuildMode` gates on the owner being allied with the player. Travel + persistence: the world is the site table `contentSites` (each site one pooled map — the home hub, the lava tube, the wild biomes — every one procedural), reached from a site's travel BEACON (the `travel` interaction) through `WorldMapUI`, whose trip `ColonyMap.travel` prices in in-game hours before `ColonyMap.go` moves the squad; `ColonyMap` also parks the per-map runtime over the `World` pool, each map generated by `ColonyLevel` from the site's seed, biome and anchor prefab on its first visit only → `SaveGame` over `Snapshot`+`Json`, which keeps every resident map as it stands (the grid through `LevelGrid.pack`, the store whole with every id) and stands it back up through `ColonyMap.restore` — a load rebuilds, spawns and re-meshes nothing. Worldgen: `LevelGen` (Core) is the level-side `Renderer` — an ordered pass list over one shared context (the terrain buffer, the claim mask, the accumulating `LevelData`), each stage reading what the stages before it laid down — and every stage is Game's (`Game/Level`): `OverworldGen` composes them the way a scene composes its passes: `GenGround` → `GenLakes` → `GenAnchor` (the site's one fixed prefab, on dry ground near the centre) → `GenWalls` → `PrefabStamp` → one `GenScatter` per kind. The result — one whole level's `LevelData` plus its terrain cells — `ColonyLevel.build` paints through `LevelData.paint`, `_generate` adding only what LevelData can't carry (the terrain ground, the collide-only statics), so a generated map is ordinary tile data from there on. A level's character is the biome profile its `meta.biome` names (`contentBiomes.BIOMES`: one section per stage — ground bands, lakes, walls, prefab tag, scatter densities, climate — a stage present exactly when its section is) and its hand-built part the anchor prefab its site names (`contentPrefabs`), so a new kind of level is a data entry over the same passes. Authoring is in-game: on the DEV scratch site (flat biome), free build (F6) lays a structure down without gate or cost, the build bar's shapes (rect/frame/line drags through `BuildMode.applyItem`) make it quick, and its capture shape writes the dragged rect out through `Blueprint.capture` — a `LevelData` off the live layers and the built entities' catalog descriptors — as the literal `contentPrefabs` takes; `Blueprint.stamp` is the same plan put down through the build path.
- Level & map layers — `Level` (one map's data: its `LevelGrid` + its `EntityStore`, pooled in `World`) over `LevelGrid` (tile layers + world↔grid conversion) over the `LevelLayer` interface, whose one implementation is `TileLayer` (a `Grid` of `TileType`); `TileEdit` (the collider-sync service owning the "edit a solid tile → remesh colliders" invariant, greedy-meshed). There is no zone channel: a region derived from the map's geometry (a roof, a floor) is a tile layer, one that belongs to a thing (a trigger area, a shelter) is an entity with a footprint component, and a whole-map property is a `meta` field — the tagged cell-id channels the grid once carried lost every consumer to the latter and were dropped. Authored map CONTENT is one shape at every scale — `LevelData`, which owns it: a `Prefab` and a generator's accumulated output are the same tiles/spawns body in origin-local coords, and `translate`/`paint` are the only ops over it — there is no level file.
- Renderer — `Renderer` (the ordered `RenderPass` list a scene owns) over the passes, each carrying its own contract: the art projection contract is owned by `RenderBillboard` (STANDING, and the SKELETAL scan over `Skeleton`+`Instance`) with `RenderMesh` (VOLUME) and `RenderWalls`/`RenderFence` (WALLS); ground/tiles are `RenderTileMap` over `VertexBuffer` (its `@typedef` documents every autotile mode, plus the material-stack options a generated map's terrain uses); atmosphere is `RenderCloudShadow`/`RenderWeather`/`RenderLighting` (which owns the screen-space overlay orientation contract); plus `RenderGrid`/`RenderDebug*`. `shMeshlit` is the one world shader and owns the shader-authoring rules.
- UI & input — `UIElement` (flexpanel tree + the `UIState` blackboard) under `UI`, which owns the fixed 1920×1080 design resolution, `applyScale`, and the layout guarantee (why no widget carries a NaN guard); the `UIComponent` widgets each document their own contract, with `UITrigger` the canonical pointer FSM and `UIDraw` the shared-primitive bucket (it owns the resolve-fonts-at-draw-time rule); the standalone singletons `Tooltip`/`Toast`/`UIPointer` (owner of the poll-once rule)/`SlotDrag`/`UINav`/`SceneTransition`/`Dialogue`/`FloatingText`; input is `Input`/`InputAction`/`InputContext` (`InputPreset` persisting the profile over them — sensitivity, deadzone, the keyboard rebinds), with `Camera.cursorWorld` owning the pitched-camera world-cursor rule.
- Collision & navigation — Core/Collision is the geometry every collision consumer shares: `AABB` (the anchor convention), `Broadphase` (the uniform-grid pair sweep), `Raycast` (nearest segment hit), `Query` (spatial lookup by component presence, point tests only). Core/Nav is `NavGrid` (the level-sized cost grid) over `MotionPlanner` (A*), queried through `PathfindingSystem`. `Grid`, the plain row-major buffer both `NavGrid` and the level layers sit on, stays a Core/Util utility.
- Presets & utilities — `EntityPreset` (declarative spawning, variant inheritance, the `scale`×`size`/density bake) over the Core/Util modules, each owning its contract: `Settings`/`Color`/`SpriteMeta` (the declared per-sprite metadata)/`I18n`/`Camera`/`Audio`/`Tween`/`Grid`/`File` (sync text + binary, async caveats)/`Json` (the ref/cycle-safe codec, compact + pretty)/`Registry` (the shared content-registry store)/`Snapshot` (the save frame)/`Log`/`Screenshot`/`Utils`.
