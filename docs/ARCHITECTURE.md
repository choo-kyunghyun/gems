# G.E.M.S. Architecture

## Overview

This file carries the layer map, the cross-cutting invariants, and the area index — and nothing per-module: a module's contracts live in JSDoc at its owning declaration.

Routing rule: the code is the primary reference. Before designing or modifying an area, read its owning files' JSDoc contracts, the invariants here, the quirks in GMRT.md, and — for anything on a per-tick or per-entity path — the costs in PERF.md. The per-area ledgers that used to sit under `docs/architecture/` are gone — their contracts now live at the owning declarations. The index below exists only to locate an area's owning files; a new contract goes to its owner, never here.

Doc laws — what this file may contain:

1. Only cross-cutting facts: the layer map, invariants binding every area, and the area index. A single-module contract lives in that module's JSDoc, never here.
2. No history. What a design replaced, when, and why lives in git — never in docs.
3. One owner per fact: GMRT quirks in GMRT.md, cross-cutting invariants here, a module contract at its owning declaration. Everyone else cites.
4. No API inventories, content catalogs, or tutorials — signatures and contracts live in JSDoc, content in its registry, GameMaker in the manual.
5. Dead or unwired code gets a clause, not a paragraph.

## Layers & Placement

The project's largest systems are the ECS system and the Flexpanel-based UI system.

Two top-level pillars (project folders), Core reusable without Game:

- `Core` — the engine, and only the engine: ECS (the `EntityStore`), the `Level`/`Scene`/`World` triad (with `WorldClock`, the in-game calendar `World` advances), zones, renderer passes (`RenderLighting` among them, over the `Light` component), sprite playback (`Animator`/`AnimationSystem`), the UI system, input, utilities. Every area references only engine concepts — space, time, presentation, entity lifecycle — and never a gameplay rule. Core never references Game (Game could be deleted and Core still builds).
- `Game` — the integrated showcase consuming Core: the app shell, the scenes (colony / editor / lobby), the whole gameplay model flattened into `Game/Component` (data: `Health`/`Stats`/`Inventory`/`Equipment`/`Faction`/the survival needs/…) and `Game/System` (behaviour + content registries: `Combat`/`InventorySystem`/`StatusSystem`/`Weather`/`Tracker`/`QuestLog`/…), the item vocabulary in `Game/Item` (the `Item`/`Rarity`/`Manufacturer` registries, over the capability classes `Weapon`/`Gun`/`Ammo`/`Equippable`/… they compose, in `Game/Item/Component`), all content- or model-specific glue (`Colony*`, `content*`, `CombatAI`), the Gems UI kit (`Game/UI/Kit`: the themed factory buckets `GemsTheme`/`GemsContainers`/`GemsWidgets`/`GemsControls` over the Core UI system), and the media assets (`Game/Media`).

Placement rule for new code: references only engine concepts (space/time/presentation/entity lifecycle) → Core; states a gameplay rule — damage, needs, economy, progression — or names specific content/scenes/`Colony*` → Game, data to `Game/Component`, behaviour and registries to `Game/System`, item definitions to `Game/Item`, an item capability class to `Game/Item/Component`, a content data table to `Game/Content` (`content*`, authored as JS — content is code, never a shipped JSON datafile). Read it through the consumers, which is what settles the near calls: `AnimationSystem` is Core because Core draw passes (`RenderBillboard`/`RenderEntity`) call it and `WorldClock` because `World` drives it, while `Combat`/`Faction`/`Interaction` are Game because every consumer is.

## Cross-Cutting Invariants

Rules that apply in every area (the GMRT quirks in [GMRT.md](GMRT.md) additionally always apply):

- ECS shape: components are string tokens (`globalThis.Position = "Position"`), each script carrying the `@typedef` that is the only definition of its data shape (they ARE the type system — the checker consumes them); systems are plain objects `{ update(entities) }`, or, for on-demand utility systems (`PathfindingSystem`), stateless objects with named query/resolve methods instead of an `update`; each `Level` owns its `EntityStore`. Nothing auto-runs systems — the active scene's `update()` dispatches them explicitly. (Store handles are canonically `entities`.)
- Level / Scene / World: a `Level` is one map's DATA — its grid and its entity store — and nothing else (it never updates or draws). A `Scene` is the behaviour: it composes a level, systems, renderer, camera and UI, and owns `update()`/`draw()`. `World` pools Levels by map id and carries the cross-map timeline. There is no scene manager: the `Game` object holds the one active scene pointer and drives it from its own events (its Create_0 owns the switch/pause contract). Exactly one scene is live and a switch destroys it — a scene is never frozen, so it carries no state across a swap.
- Composition over inheritance — GMRT breaks subclassing (`super` faults, base-class field initializers don't run — see GMRT.md): "kinds of X" are a flat class plus a `components: []` queried by `instanceof` (`Item`, `UIElement`); scene screens are standalone classes satisfying the duck-typed `Scene` contract, never `extends Scene`.
- Singleton shape: a global with one live instance is a plain object (`globalThis.World = { … }`), state held as ordinary properties — the form the systems and namespaces already use (`World`, `Log`, `Combat`, every `*System`). A static-only class buys nothing here (no instances, no `instanceof`, inheritance broken regardless) and takes on two class-only GMRT defects, the ~50-method cliff (#15065) and the static-initializer trap (GMRT.md): write no new ones. A class with one live instance that owns a lifecycle is NOT a singleton — `LevelGen` is an instance class, shaped and named as such. A family of singletons stays FLAT, grouped by a name prefix and composed by its head at boot/reset (`Audio`/`AudioListener`/`Music`, `World`/`SimClock`/`WorldClock`/`WorldEvents`, `Render*`), and callers reach the leaf directly; a member mirroring a singleton (`X.sub = Sub`) is a second name for one object plus a boot-wiring dependency, so a member only ever holds data (`World.levels`, the level pool).
- The clock split (pause/dilation rule): `Time.delta` is scaled by `Time.scale`, so anything on it freezes/slows with the sim — gameplay motion wants exactly that, but UI timers/easing must use `Time.raw` (hover/press fades, caret blink, key-repeat, toggle easing — `UIButton`/`UIInput`/`UICheckbox`; likewise the GUI singletons `Toast`/`SceneTransition`/`Dialogue`), else menus freeze while the game is paused. World-space effects deliberately stay on `Time.delta` so slow-mo slows them too (`FloatingText`, `Weather`).
- Hot-path idioms: the runtime is a VM, so per-element constants decide the frame, not complexity class ([PERF.md](PERF.md) owns the costs and the full list). The two that bind every area: a per-tick system iterates with `entities.forEach(tokens, fn)` and reads its components off the callback, never `query` + a `get` per entity (`query` stays for a materialised id list that outlives the scan); and geometry in a pair sweep writes into a caller-owned `AABB.rect()` scratch through `edgesInto`/`ofInto` rather than allocating per test.
- Live queries over stored handles: entity ids are never held across frames/maps — consumers re-derive them by component-presence query each use (`scene.playerId` from `Playable`, the camera target from `CameraFocus`, NPCs/portals/enemies by `entities.query`/`Query`). Markers are components, not tag strings.
- AABB convention: every collision/geometry consumer derives world-space edges through `AABB.edges(pos, box)` / `AABB.of(entities, id)` — never inline `pos.x + box.x` (the non-uniform BBox anchor lives in one place).
- Injection idiom: a module stays model-agnostic by exposing a hook its consumer wires at scene setup — Core to Game (`RenderLighting`'s `ambient`, `UIQuestTracker`'s `source`) and, inside Game, a system to the scene that owns the stat model (`Combat.mitigate`, `StatusSystem.onStatsChanged`, `ConsumableSystem.grantAttr`, all wired in `sceneColony.create`). Extend through the seam; never make Core reach down into Game.
- Registry pattern: content is data registered into flat registries keyed by string id (`Item`/`Rarity`/`Manufacturer`/`Status`/`Recipe`/`Prefab`/`InteractAction`/`EntityPreset`/`StateSystem`) — adding content is a data entry, not an engine edit. Registration runs from `create()`-time calls (`content.register()`), never at script top level (load order). The id-keyed, insertion-ordered ones are thin facades over the shared `Registry` ops, which own that store's contract.
- Serialization-safe data: persisted blobs (Settings/InputPreset, zone `data`, `entities.export`/`EntitySnapshot`) may nest — serialize them with GML `json_stringify` (the interop workaround), or, when the data carries sprite refs or can cycle, the `Json` codec; both are nesting-safe where JS `JSON.stringify` faults (see GMRT.md). The hard rule that remains: no `Set` in serialized fields (GMRT Set iteration crashes). Dense/large arrays still go to binary blobs, not JSON (see `File` / the Snapshot hybrid).

## Area Index (owning files)

Each entry names an area's owning files, so you can find where a contract lives. The contract itself is in the code — read the file, not a summary of it.

- Game shell & UI kit — `objects/Game/` (the per-event wiring; each event's order is a contract, and Create_0 owns the scene pointer + its switch/pause lifecycle), `Scene` (the duck-typed screen contract) with `SceneTransition` (the swap fade), `sceneLobby` (boot scene + dev launcher) and `demo` (`SceneRegistry`, `teardownScene`), plus the Gems UI kit: `GemsTheme` (palettes + the kit-wide contracts) with the `GemsContainers`/`GemsWidgets`/`GemsControls` factory buckets and the gems-composed overlay singletons `SystemMenu` (the app's pause menu — the Game object hands itself to its update(), and its quit target is boot-wired) and `VirtualKeyboard`.
- ECS core & simulation — `EntityStore` (the per-level store) over `ComponentStore` (SoA columns) + `EntityID` (generational ids), `EntitySnapshot` (single-entity capture/migrate), and `World` (the map-id → `Level` pool, whole-entity take/put/transfer between them, and the world timeline it delegates to `WorldClock`/`WorldEvents`); fixed-rate simulation in `SimClock` (ticks + `alpha`, and the tick-loop ordering contract) and `Time`; the built-in systems, each owning its own contract (`Movement`/`Solid`/`Separation`/`State`/`Lifetime`/`Interpolation`/`Pathfinding`/`Animation`/`Instance`/`Skeleton`); pathfinding via `PathfindingSystem` → `PathFollow` (the consumer-side walker + terrain cost) over `MotionPlanner`/`NavGrid`.
- Genre controllers — a genre layers a player brain over the Core systems: the colony's is an ECS system (`PlayerSystem` driving the `Playable` component, at the head of the scene's physics sequence). A genre picks the `Game/System` modules it wants, and each module owns its contract in its own JSDoc.
- The colony sim — the reference consumer, and the largest area. `sceneColony.update` is the reference orchestration; `ColonyCombat` holds the combat/loot plumbing and the `Mortal` death pair. Content is `Item`/`Rarity`/`Manufacturer` + the capability components (`Weapon`/`Gun`/`Ammo`/`WeaponMod`/…), with `Attributes`→`StatModel` deriving `Stats`, `Combat` applying all damage, and `CombatAI` driving every non-player combatant. Paper-doll art is `Appearance`+`AppearanceSystem` over the `spr_human` strip (template contract in `tools/pixel-art-kit`). Genre UI: `StorageUI`/`TradeUI`/`CraftingUI`/`WeaponModUI`/`BuildMode`/`InventoryUI`/`WorldOverlay`, refresh-driven by `Interactable`. The world-sim is `Weather`/`Temperature` over the Core `WorldClock`, with `RenderWeather`/`RenderCloudShadow` reading them. Persistence: `ColonyMap` (portal travel + the per-map runtime it parks over the `World` pool, built from a level file by `ColonyLevel`) → `SaveGame` over `Snapshot`+`Json`, with `Blueprint` replaying builds. Worldgen: a composed `LevelGen` (`AuthoredStamp`/`PrefabStamp`/`OverworldGen`/`TerrainField`/`Prefab`) accumulates one whole level's `LevelData` at build, which `ColonyLevel.build` paints through the same call an authored file takes — `_generate` adds only what LevelData can't carry (the terrain ground, the collide-only statics), so a generated map is ordinary tile data from there on.
- Level & map layers — `Level` (one map's data: its `LevelGrid` + its `EntityStore`, pooled in `World`) over `LevelGrid` (tile layers + zone channels + world↔grid conversion) over the `LevelLayer` interface, whose one implementation is `TileLayer` (a `Grid` of `TileType`); `TileEdit` (the collider-sync service owning the "edit a solid tile → remesh colliders" invariant, greedy-meshed); zones as `Zone`/`ZoneMap` (one channel, one zone per cell — a point-wise spatial index, with no per-entity membership and no system behind it; a consumer wanting a border-cross edge caches the last id it read). Authored map CONTENT is one shape at every scale — `LevelData`, which owns it: a level file, a `Prefab`, and a generator's accumulated output are the same tiles/zones/spawns body in origin-local coords, and `translate`/`paint` are the only ops over it.
- Renderer — `Renderer` (the ordered `RenderPass` list a scene owns) over the passes, each carrying its own contract: the art projection contract is owned by `RenderBillboard` (STANDING, and the SKELETAL scan over `Skeleton`+`Instance`) with `RenderMesh` (VOLUME) and `RenderWalls` (WALLS); ground/tiles are `RenderTileMap` over `VertexBuffer` (its `@typedef` documents every autotile mode, plus the material-stack options a generated map's terrain uses); atmosphere is `RenderCloudShadow`/`RenderWeather`/`RenderLighting` (which owns the screen-space overlay orientation contract); plus `RenderZone`/`RenderGrid`/`RenderDebug*`. `sh_meshlit` is the one world shader and owns the shader-authoring rules.
- UI & input — `UIElement` (flexpanel tree + the `UIState` blackboard) under `UI`, which owns the fixed 1920×1080 design resolution, `applyScale`, and the layout guarantee (why no widget carries a NaN guard); the `UIComponent` widgets each document their own contract, with `UITrigger` the canonical pointer FSM and `UIDraw` the shared-primitive bucket (it owns the resolve-fonts-at-draw-time rule); the standalone singletons `Tooltip`/`Toast`/`UIPointer` (owner of the poll-once rule)/`SlotDrag`/`UINav`/`SceneTransition`/`Dialogue`/`FloatingText`; input is `Input`/`InputAction`/`InputContext`, with `Camera.cursorWorld` owning the pitched-camera world-cursor rule.
- Presets, query & utilities — `EntityPreset` (declarative spawning, variant inheritance, the `scale`×`size`/density bake) and `Query` (spatial lookup by component presence), over the Core/Util modules, each owning its contract: `Settings`/`Color`/`SpriteMeta` (the declared per-sprite metadata)/`I18n`/`Camera`/`Audio`/`Tween`/`MotionPlanner`/`AABB`/`Broadphase`/`Raycast`/`File` (sync text + binary, async caveats)/`Json` (the ref/cycle-safe codec, compact + pretty)/`Registry` (the shared content-registry store)/`Snapshot` (the save frame)/`Log`/`Screenshot`/`Debug`/`DebugInspector`/`Utils`.
