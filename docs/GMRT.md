# GMRT

Runtime-quirk reference for **G.E.M.S.** on the GMRT runtime, imported into context by [CLAUDE.md](../CLAUDE.md) (via its `@docs/GMRT.md` line) so it is always loaded alongside it.

**Everything below is verified against GMRT 0.20** (the toolchain pinned by `gm-options.json`) — re-audit this document on a runtime upgrade; fixes flagged **0.22** land in that release. Every entry was A/B-run in a dedicated test-bed on GMRT 0.20 vs GMS2 (and vs Node as the ES2020 oracle for JS) and deduped against `YoYoGames/GameMaker-Bugs`; every tracked issue carries its ticket as **[#00000]**. The test-bed project is gone — rebuild a sample project when filing.

Working rules: avoid the quirks, don't "clean up" code back into them, leave a one-line comment where a quirk forces an unusual idiom so it isn't "fixed" back, and record new quirks here as found — an entry states the rule, its ticket/version, and the safe idiom, never probe dates, run output, or discovery narration (report those in conversation). **Before logging a new one, prove it's real:** `gm-cli manual read <fn>` (it may be documented behaviour), then `gh search issues --repo YoYoGames/GameMaker-Bugs` (it may already be ticketed — thumbs-up/comment, don't duplicate). A divergence that reproduces on **both** runtimes is general GameMaker behaviour, not a GMRT bug — record it as an idiom (§4) if it needs a rule, file nothing.

Organised by ownership/status: **§1 Reported & tracked** (ticketed GMRT bugs) · **§2 Unreported / not filing** (verified divergences without their own ticket) · **§3 Officially unsupported** (declared gaps) · **§4 Project idioms** (our safety rules — not GMRT defects) · **§5 Capabilities** (verified working). Area-scoped rules (UI first-frame guards, camera/cursor conversion, shader conventions) live at their area's owner (owning JSDoc; the frozen [docs/architecture/](architecture/) ledgers until migrated), not here — this file keeps only what can bite in **any** script.

## 1. Reported & tracked

Genuine GMRT bugs with a ticket on `YoYoGames/GameMaker-Bugs`.

### JavaScript / compiler

- [#15095](https://github.com/YoYoGames/GameMaker-Bugs/issues/15095) (open) — **`for...of` over a `Map` iterator hangs the game**: the iterator's `next()` never advances, so iterating `.values()`/`.keys()`/`.entries()` or the bare `Map` loops forever — no exception, no crash, `game.log` just stops at its last flush. Keep parallel arrays and index-loop (see `World._keys`/`_storages`). `Set` iteration works (bare `Set` and `Set.values()`); `for...of` over an array/string and `for...in` over a plain object are fine.
- [#15567](https://github.com/YoYoGames/GameMaker-Bugs/issues/15567) (open) — **a `Map`/`Set` keyed by an OBJECT (asset ref, array, or plain object) crashes natively**: `Bad optional access`, hard process death, not a JS exception, so `Log.exception` records nothing (minimal: `new Set().add({})`). String/number-keyed Maps and Sets are fine (`Item`/`Rarity`/`I18n`/…). For any object-identity membership test use **parallel arrays + an `===` identity scan** — asset-ref and object `===` both work (see `SpriteMeta`'s ref lookup, `Json._onPath`'s ancestor scan). (Distinct from #15095, the iterator hang.)
- [#15549](https://github.com/YoYoGames/GameMaker-Bugs/issues/15549) (open) — **short-circuit `&&`/`||` corrupts its LEFT operand**: codegen for `const r = b && expr` writes the operator's _result_ back into `b`'s own local, so `b` flips whenever the result differs (`let b = true; const r = b && false;` → `b === false`). BOTH `&&` and `||` do it; only `?:` is safe. This was the root cause of the old "a cached primitive boolean can flip mid-function" mystery — never reuse a variable after it has been a `&&`/`||` left operand; caching the component object and reading the property live (`PlatformerController.update` → `groundedComp.isGrounded`) remains a safe pattern.
- [#15079](https://github.com/YoYoGames/GameMaker-Bugs/issues/15079) (open) — **no optional chaining (`?.`)**: any `a?.b` crashes the compiler (`Visit function for ?. expression not found`), not a code error pointing at the offending line. Write the guard explicitly (`a !== null && a !== undefined ? a.b : fallback`, or an `if`). **Nullish `??` and `??=` are fine** — exact null/undefined-only semantics (`0 ?? 7` → `0`); `??` is already used project-wide.
- [#15194](https://github.com/YoYoGames/GameMaker-Bugs/issues/15194) (open) — **no array destructuring in a `for...of` header**: `for (const [a,b] of arr)` throws `ReferenceError: a is not defined`. Use `arr[i][0]`, or destructure inside the loop body. (Object destructuring and a `.forEach(([a,b]) => …)` param are fine — only the loop header is broken.)
- [#15566](https://github.com/YoYoGames/GameMaker-Bugs/issues/15566) (open) — **no empty `for` initializer — fails the BUILD**: `for (; c<n; c++)` in a `.js` file stops `gm-cli compile`; no game is produced (GML `for (;;)` builds fine on both runtimes — JS-compiler-only). Add an initializer or use `while`.
- [#15065](https://github.com/YoYoGames/GameMaker-Bugs/issues/15065) (fix slated for **0.22**, in QA) — **a class with >50 methods faults**: 50 OK; calling the 51st method throws `Invalid call target`. Split a fat class into collaborators, lift helpers into free functions / a `globalThis` module object, or use composition (a flat base + `components:[]` queried by `instanceof`, as `UIElement`/`Item` do). The 0.22 upgrade lifts the ceiling (then e.g. `UIElement`'s commented-out flexpanel setters can return).
- [#15067](https://github.com/YoYoGames/GameMaker-Bugs/issues/15067) (open) — **class inheritance / `super` is broken**: `super.method()` is a compile error (`Unsupported expression [ R_SUPER="super" ]`), and the implicit parent-constructor chain never runs — constructing a subclass skips the **BASE** class's field initializers/constructor, leaving inherited fields `undefined` (`class Bar { a = 1 }` / `class Foo extends Bar { b = 2 }` → `b` is `2` but `a` is `undefined`; the subclass's OWN field initializers do run). Model "kinds of X" as composition (`addComponent`/`getComponent(Class)`, `instanceof` on a flat class); anything a base class would have initialized must be assigned in a method that runs (e.g. `create()`).
- [#15564](https://github.com/YoYoGames/GameMaker-Bugs/issues/15564) (open) — **past ~200–250 top-level `function` declarations per file, some stop hoisting** and the game faults at startup (`cannot coerce undefined or null…` / `unable to access property`). Assign explicitly (`globalThis.X = function X(…)`) and keep files small (why the GemsUI kit is split). (Same count-limit family as #15065, but a distinct bug — different threshold and error.)
- [#15563](https://github.com/YoYoGames/GameMaker-Bugs/issues/15563) (open) — **`toUpperCase()`/`toLowerCase()` return garbage Unicode**, even for ASCII (`"q".toUpperCase()` → `"ଊ"`); GML `string_upper`/`string_lower` are correct. Map case via char codes (`String.fromCharCode(c-32)` for a–z→A–Z; see `VirtualKeyboard._upper`, `InvTable.lower`).
- [#15565](https://github.com/YoYoGames/GameMaker-Bugs/issues/15565) (open) — **`JSON.stringify` faults natively on nested objects/arrays**: a flat `{key: scalar}` is fine; a value that's an object/array kills the process (flat output is also pretty-printed, and `1` → `1.0` — the latter is shared built-in behaviour). **Workaround: call GML `json_stringify()` on the JS object** — a JS object IS a GML struct (interop idiom, §4), so it serializes nested data crash-free and compact; read it back with native `JSON.parse` (parse handles nesting — only stringify faults). This is the project idiom for structured disk blobs: `SaveData`/`Settings`/`Profile`/`Achievement`/`Settlement` store native objects/arrays directly, and the `Json` codec wraps `json_stringify`'s job with ref-tagging + cycle-safety for save-game bundles.
- [#15593](https://github.com/YoYoGames/GameMaker-Bugs/issues/15593) (open) — **`Array.prototype.sort` violates ES2020 twice: the comparator's return is truncated toward zero (return a SIGN, not a raw difference), and the sort is NOT stable**: a fractional `(a, b) => a.t - b.t` over sub-1 gaps makes every pair "equal", and because ties are also reordered (even with a plain integer comparator — an always-`0` comparator scrambles `[1..12]`) the result is an **arbitrary shuffle of the ties**, not a no-op. Return `a < b ? -1 : a > b ? 1 : 0` (see `Raycast.castAll`) — a difference comparator only happens to work for far-enough-apart integers — and when tie order matters, break ties explicitly in the comparator (e.g. carry an index), never rely on input order. Same truncation in GML `array_sort` — but there it matches the manual's letter (integer-only comparator), and it's **GMS2 that sorts** the same code (a silent porting divergence).
- [#15597](https://github.com/YoYoGames/GameMaker-Bugs/issues/15597) (open) — **a top-level/event-body `var` named after a GML built-in resolves to the BUILT-IN, not the local**: GML built-ins are in scope in JS (the interop idiom, §4) and the `var` binding never comes into existence — every read yields the built-in, even above the `var` line. A function name (`var frac`, `var round`) turns any method call on the local into `TypeError: Invalid call target` and arithmetic into garbage strings (`var frac = 0.5; frac + 1` → `"function frac1"`); a constant name (`var pi = 3; pi + 1` → `4.14159…`) silently reads as the constant. **`let`, `const`, function parameters, and `var` inside a declared function body all shadow correctly** — why the project's `const frac`/`let power`/`const fps`/`const max` locals are safe — as do instance-variable names (`x`) and GML's own `var` (which hoists and shadows even on GMRT; legacy GMS2 rejects the colliding name at compile time). The project uses `let`/`const` exclusively — never introduce `var`, and prefer non-colliding names regardless. This was the "intermittent `.sort()` crash" mystery: the trigger was the array being named `frac`, never the sort (distinct from #15593, the sort-semantics bug).

### Runtime / rendering

- [#15546](https://github.com/YoYoGames/GameMaker-Bugs/issues/15546) (open) — **`merge_colour` FLOORS its channel math where GMS2 rounds** — so don't ease a _packed_ color int every frame; ease its float r/g/b channels. Two traps, both acute at high/unlimited FPS (tiny per-frame `t`): (1) `merge_color(c1, c2, t)` floors `c1*(1-t)` and `c2*t` separately, so even `merge_color(c, c, t)` returns `c` minus ~1/channel — re-merging its own result every frame drifts the color to **black**; (2) a _rounded_ packed-int lerp instead loses a sub-1 per-frame step (`round(c + 0.4) == c`), so the tween **freezes**. One-shot merges are fine (`Color.merge`, day/night ambient). For an animated color, keep the `r/g/b` as **floats** and `Tween.approach()` each channel, rounding only the final `make_colour_rgb` (see `UIButton._easeColor`).
- [#14737](https://github.com/YoYoGames/GameMaker-Bugs/issues/14737) (open — Ready for QA, fix not shipped, so still present in 0.20; the ticket's version field is a known IDE mislabel) — **the fixed-function alpha test is INERT — `discard` in a fragment shader instead**: `gpu_set_alphatestenable`/`gpu_set_alphatestref` round-trip through their getters but have **no effect at draw time** — a transparent fragment is not discarded, so it still writes depth (with the depth buffer on, a sprite's empty pixels occlude what's behind — the 2.5D billboard bug). Do the cutout in the **fragment shader** — `sh_meshlit`'s **`u_alphaRef`** uniform (0 = off; billboards pass ~0.5) `discard`s fragments whose `gm_BaseTexture` **texel** alpha is below it; a discarded fragment writes no depth. Discard on the texel alpha (sprite SHAPE), **not** the final `v_vColour*tex`, so a dimmed/tinted entity stays fully visible. `RenderBillboard` sets it around its draw loop; `RenderMesh._setupLights` pins it 0 so vox/wall submits never discard. A custom shader _disables_ the fixed-function alpha test anyway, so the shader doing its own `discard` is the correct approach, not merely a workaround (`gpu_set_alphatestenable(true)` stays commented out in `obj_game` Create_0 as a record of the dead end).
- [#15140](https://github.com/YoYoGames/GameMaker-Bugs/issues/15140) (closed — **fixed in 0.21**, so still live on pinned 0.20) — **`rectangle_in_rectangle` misses real overlaps — don't use it as an overlap test**: on 0.20 the containment return is direction-swapped (source fully inside destination → `0`, the manual's documented `1` case; destination inside source → `1`) and a **cross-shaped overlap** (rects overlap but neither holds a corner of the other) also returns `0` — measured, `> 0` misses ~25% of genuinely overlapping random pairs. It's also no faster from JS anyway (~equal to an `AABB.overlap` call incl. per-call GML interop, both slower than the inline four-compare), so overlap tests stay on **`AABB.overlap`** even after 0.21. `point_in_rectangle` is unaffected (matches the inline JS point test exactly; edges inclusive) — the UI hit-testing use is fine. On correct runtimes the function is a symmetric overlap test despite the manual's source/destination framing ([#10623](https://github.com/YoYoGames/GameMaker-Bugs/issues/10623): `src⊂dst` → `1`, `dst⊂src` → `2`).
- **`gpu_set_scissor` quirk cluster** — it is the UI clip mechanism (`UIElement._drawClipped` clips scroll/viewport children with it: reliable, no leaks, draws directly to the back buffer — crisp SDF text, no clip surfaces; nested scrolls clip by intersecting rects). The rules:
  1. Coords are render-target **PIXELS**, not GUI units — convert by `k = target/gui`. ([#11377](https://github.com/YoYoGames/GameMaker-Bugs/issues/11377) — confirmed **intended** behaviour, not a bug.)
  2. [#15476](https://github.com/YoYoGames/GameMaker-Bugs/issues/15476) (**fixed in 0.22**) — the render target is the **window back buffer**, and `window_get_width/height()` / the application surface lag it on a resize (a SHRINK resizes the back buffer synchronously, a GROW lags one frame) — a scissor sized from any single query can overflow the target on a resize frame → a **fatal** "scissor rect not contained in the render target" error. Until 0.22, size clips from **`Display.clipW/clipH`** (the intended size min'd with its 1-frame-lagged self, which never exceeds the live back buffer in either direction).
  3. The scissor is **not cleared between frames** — a stale rect survives and, after a shrink, replays forever as a bogus "nested parent". `UI.draw()` re-anchors it to the full target (`gpu_set_scissor(0, 0, Display.clipW(), Display.clipH())`) at the start of each frame.
  4. `gpu_get_scissor()` returns `{0,0,0,0}` when unset (the full-target default) — treat it as a nesting parent only when its `w`/`h` are positive, and **never restore a saved `{0,0,0,0}`** (that clips everything afterward to an empty rect); at top level reset to the full render target instead.
  5. [#6523](https://github.com/YoYoGames/GameMaker-Bugs/issues/6523) (fixed on GMS2 2024.8, **not yet on GMRT**) — **setting the scissor does NOT flush the pending vertex batch**. Three symptoms: the LAST item drawn under a clip renders UNCLIPPED (it flushes later, after the restore) → `draw_flush()` at the end of `_drawClipped` **before** the scissor restore; the still-pending last primitive of the PRECEDING drawer gets captured under the clip and clipped away → the preceding drawer must end with a harmless trailing untextured primitive to force the flush (`UITabs.onDraw` re-strokes its baseline last) — a _start_-of-clip `draw_flush()` instead corrupts the clip (`No pipeline set`/`Invalid CommandBuffer`); a non-clipped sibling drawn AFTER a clip in the same parent can render nothing → `CraftingUI` avoids any clip in its master-detail row (see its comment). `draw_flush` is manual-flagged debug-only but is the only batch-flush primitive — once per clip container per frame is fine. A text-only clip (caret/overflow in one widget) can compute the visible substring itself (`UIInput.onDraw`).

## 2. Unreported / not filing

Verified GMRT divergences without their own ticket — filing status inline.

- **No TDZ for `const` — an early read yields `undefined` instead of throwing** (`let` is correct: its early read throws the mandated `ReferenceError`, at top level and in function bodies alike): the `const` binding hoists and correctly shadows any same-named GML built-in from the top of its scope, but reading it above its declaration returns `undefined` where ES2020 mandates a `ReferenceError` — a use-before-declaration bug on a `const` fails silently instead of loudly. Keep declarations above first use; `checkJs` flags straight-line use-before-declare. _Unreported._
- **Chained 32-bit xorshift PRNGs compute silently WRONG values** — `s ^= s<<13; s ^= s>>17; s ^= s<<5` diverges from real JS int32 semantics (GMRT bitwise uses GML 64-bit numbers, not ES2020 ToInt32; e.g. seed `123456789` is wrong from its 2nd round vs Node) and nothing ever throws. Use integer-float math with no bitwise — a Park–Miller MINSTD LCG (`s = (s*48271) % 2147483647`); **`Rand`** (`scripts/Rand/`, Core/Util) is the one home for the idiom — use it, don't hand-roll another copy. (Single bitwise ops like `EntityID`'s id packing are fine; only the overflowing chain breaks.) _Not filing — a deliberate consequence of GMRT's number model (NaN-boxed doubles/int64, no int32 type); the theme is already open as [#15060](https://github.com/YoYoGames/GameMaker-Bugs/issues/15060) / [#11835](https://github.com/YoYoGames/GameMaker-Bugs/issues/11835) — comment there rather than filing new._
- **A `static` field initializer can't reference its own class** — `static x = ClassName.y` throws at load (class binding in TDZ), and `static x = this.y` **silently reads the WRONG value** (`0`) — `this` is not a workaround; only a literal is safe. Use a static method, or assign `Foo.x = …` after the class body (ES2015); referencing another already-loaded class is fine. (Note: JS class statics init _eagerly_ on GMRT; GML constructor statics are lazy — a separate, documented mechanism.) _Not filing — public static class fields are ES2022, outside GMRT's ES2020 target._

## 3. Officially unsupported (release notes — "Known Incompatibilities with GMS2 runtimes")

Declared, not discovered: the release notes list these as features that work on the legacy GMS2 runtime but are **not yet supported on GMRT**. Don't burn a probe run re-discovering one, and don't read its absence as a project bug.

- **Prefabs** — GameMaker's asset-prefab feature. Unrelated to the project's own `Prefab` registry (`scripts/Prefab/`, plain JS — unaffected).
- **Video playback** (scoped "other platforms" in the notes) — `video_*` is unused by the project; treat as unavailable.
- **SVG Assets** — `sprite_get_number()` returns `0` for an SVG, so frame math can go negative and `draw_sprite_ext` throws. Use raster sprites; clamp frame count `≥1` and `subimg` `≥0` (see `AnimationSystem`). The remaining SVG assets: `spr_choo`/`spr_play`/`spr_exit`/`spr_back`/`spr_revert`.
- **`flexpanel_node_get_measure()` / `flexpanel_node_set_measure()`** — Yoga's custom measure-callback hook is absent, so a widget cannot self-size via a measure function; explicit style mutation is the self-size mechanism (see the flexpanel idiom, §4).
- **`vertex_buffer_exists()` / `vertex_format_exists()`** — no existence probes for vertex buffers/formats; keep your own handle bookkeeping (`RenderMesh`'s vbuf cache holds its handles and never re-validates them).
- **`application_surface_is_draw_enabled()`** — absent; mind it when porting GMS2 samples.
- **Lots of error spam from SDL** — upstream-acknowledged runner console noise; don't chase SDL-looking errors in `gm-cli run` output as project faults unless the game also misbehaves.

## 4. Project idioms (not GMRT defects)

How the project stays safe on top of documented GameMaker behaviour — design rules and workarounds. Nothing here is reportable.

- **JavaScript is GMRT-only — the GMS2 toolchain silently DROPS `.js` events and `.js` scripts** (verified with a switchable demo): GMS2 builds and runs with no error or warning and the `.js` body simply never executes, even when the event has no `.gml` at all. All of G.E.M.S.'s JS is dead code under GMS2; any dual-runtime experiment needs `.gml`. (Also: a `.js` GMScript's top-level code auto-runs at startup on GMRT.)
- **JS objects/arrays ARE GML structs/arrays — pass them straight to GML built-ins.** `json_stringify(jsObj)`, `variable_struct_get_names`/`_get`/`_exists`, `is_array`/`array_length` all operate on JS data directly (verified on nested objects: `json_stringify({a:1,b:[1,2,3],c:{d:"x"}})` → `{"a":1.0,"b":[1.0,2.0,3.0],"c":{"d":"x"}}`). This interop is the workaround for the `JSON.stringify` crash ([#15565](https://github.com/YoYoGames/GameMaker-Bugs/issues/15565), §1).
- **Top-level bare `const` isn't visible to other scripts** — module-like per-file scoping, not a bug; share via `globalThis.Name`. (The hoisting FAILURE past ~200 top-level functions is a bug — [#15564](https://github.com/YoYoGames/GameMaker-Bugs/issues/15564), §1.)
- **An asset ref reflects as an empty object** — `typeof` is `"object"`, `is_struct` is even `true`, and `Object.keys(ref)` is `[]` without throwing, so a generic deep copy silently turns a stored sprite handle into `{}`. It's a GM handle; JS reflection cannot identify one: discriminate plain data by `v.constructor === Object` (`true` for object literals, `false` for asset refs) and pass refs through by reference (see `EntityPreset._clone`); asset-validate with GM functions (`sprite_exists`/`object_exists`/`asset_get_type`), which safely reject non-asset data. Likewise documented: `asset_get_index(name)` returns an asset handle, not a number (`is_real()` is false on both runtimes; a missing name is `-1`).
- **flexpanel: runtime style mutation works — follow the design rule** — `flexpanel_node_style_set_*` + `flexpanel_calculate_layout` applies; `UIText`/`UIRichText` use it to self-size in `onUpdate` (so a `gemsLabel` reports a real width/height). **By choice the broader live-layout drivers (scroll, drag, slider fill) stay on the draw-time offset/clip pattern** — they work, migrating is churn — and `UIElement`'s ~45 commented-out setters stay commented (re-enabling all would pass the 50-method ceiling — until the 0.22 fix for [#15065](https://github.com/YoYoGames/GameMaker-Bugs/issues/15065) lands; enable one on demand, minding the count). Set fixed layout props **once at construction**; drive runtime change with **draw-time offset/clip math** (`UIInput`/`UISlider`); show/hide a subtree with `child.enabled`, not `display`. **Structural** mutation is reliable: `insertChild`/`removeChild` → `markDirty` reflows correctly (as `UIAccordion` does) — when a layout must change _size_, insert/remove the subtree; a same-size show/hide prefers `enabled`. Property reference: `gm-cli manual read "Flex Panel Struct Members"`; Yoga docs (https://www.yogalayout.dev/docs/styling/) cover the semantics. (Measure-callback self-sizing is officially unsupported, §3 — style mutation IS the self-size mechanism.)

## 5. Capabilities (verified working — use directly, don't avoid)

- **`console.log()` works in JS events** — behaves like `show_debug_message()`. Guard GML-only calls (`try { game_end(); } catch (e) {}`) and the identical `.js` file also runs under Node for an ES2020 baseline.
- **Getters/accessors work** — instance and `static` get/set, computed bodies and GM-flavored names (`index`/`value`/`depth`) included; the old 0.19/0.20 miscompile/fault reports were dismissed by the re-audit. The existing method conventions (`isOpen()`, `getIndex()`, "no static getters") are house style — keep them, don't churn, but new code needn't avoid accessors.
- **Trig + `draw_triangle_color`/`draw_line_width_color`/`draw_circle_color` work.** `draw_line_width_color` rendered nothing on 0.19 — on 0.20 it draws in both GUI and world/matrix-camera space (probe-verified); the render passes' plain `draw_line` is a legacy of that bug, migrate only when touching. UI arrows/chevrons go through `drawUIArrow`, check/dash markers through `drawUICheck` (both in `scripts/UIDraw`); `draw_circle_color` draws `RenderLighting`'s light blobs. Trig (`Math.PI`/`cos`/`sin`/`atan2`) is used directly (`Temperature.diurnal` cosine curve, `RenderWeather` snow sway). **`WorldClock.tint`/`_KF` keeps its hand-authored keyframe table by design — don't "trig-ify" it.**
- **Off-screen surfaces + `surface_getpixel`, `bm_add`, and multiply via `gpu_set_blendmode_ext(bm_dest_colour, bm_zero)`** (no `bm_multiply` constant) work — the `RenderLighting` 2D light-map infra.
- **Baked-mesh vertex buffers work** — `buffer_load` of an included binary → `vertex_create_buffer_from_buffer` → `vertex_freeze` → `vertex_submit(vb, pr_trianglelist, -1)` (untextured, custom `position_3d + colour + texcoord` format) renders vertex-colored 3D geometry in the depth pass. Colour byte order in buffer memory is **R,G,B,A**; the binary layout and the in-engine format declaration are a lockstep pair (24 B/vertex) — see `tools/vox-kit/vox2vbuf.py` ↔ `RenderMesh._model`. The colour is UNSHADED **albedo** and the texcoord carries a **packed face normal** (`u = nx, v = ny`, shader derives `nz = -sqrt(1-u²-v²)` — no bottom faces are emitted, so `nz ≤ 0`): `sh_meshlit` lights it live (N·L directional sun + point-light **uniform arrays** — `shader_set_uniform_f_array` works; GLSL ES `mat3(mat4)`, `#define`, and loop `break` all compile). The texcoord can carry real UVs instead **only via the shader's textured mode** (`u_useTex` = 1 + a per-submit `u_normal` uniform — how `RenderWalls` textures wall faces with the same 24 B format); a per-vertex-normal + UV combination would need a format split.
